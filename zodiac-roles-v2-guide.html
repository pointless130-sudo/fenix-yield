Background

What the Roles Modifier does, in one minute

The Zodiac Roles Modifier is an audited module by Gnosis Guild that attaches to a Gnosis Safe and lets you grant a third-party address a role: a narrowly scoped permission to execute specific functions on specific contracts through the Safe, without being a Safe owner and without per-transaction approval.

It is the cleanest primitive that exists today for non-custodial automation. A bot can be allowed to call submit() on Lido and add_liquidity() on a Curve pool, while the same bot is cryptographically incapable of transferring funds out, changing Safe owners, or calling anything not on its list. Every boundary is enforced on-chain by the module itself — if the operator's server is fully compromised, the attacker inherits only the whitelist.

The permission model has two layers, and this is the root of most of the failures below:

LayerCallAnswers
TargetallowTarget / scopeTarget"May this role interact with contract X at all, and may it send ETH there?"
FunctionallowFunction / scopeFunction"May this role call selector Y on contract X?"

Execution then happens through a single entry point on the module:

// The role member calls the *module*, never the Safe directly
function execTransactionWithRole(
  address to, uint256 value, bytes calldata data,
  uint8 operation, uint16 role, bool shouldRevert
) returns (bool success);
💡Set shouldRevert = true in production. With false, a rejected call returns success = false instead of reverting — and if you forget to check the return value, your automation will happily believe it staked funds that never moved.
Gotcha 01

allowFunction alone silently fails

The most expensive mistake in the whole stack, because it looks like it worked. You scope the function selector, the permission transaction confirms, the explorer shows your config call succeeded — and then every execTransactionWithRole reverts (or worse, returns false) with an unhelpful error.

The module evaluates the target layer first. If the target contract was never allowed for the role, the function-level permission is unreachable dead configuration. Both calls are required, per protocol address, every time:

// ❌ WRONG — confirms on-chain, permission never takes effect
await roles.allowFunction(ROLE, LIDO, SELECTOR_SUBMIT, options);

// ✅ RIGHT — target first, then function
await roles.allowTarget(ROLE, LIDO, targetOptions);
await roles.allowFunction(ROLE, LIDO, SELECTOR_SUBMIT, fnOptions);

Nothing warns you about the missing half. The config transaction succeeding is not evidence the permission works — only an actual execution test is (see the verification checklist).

Gotcha 02

The ETH "Send" bitmask on allowTarget

The options argument on allowTarget is a bitmask controlling ETH value transfer and delegatecall. Get it wrong and calls revert with no error that mentions value at all.

The rule: any protocol whose entry function is payable — i.e. your transaction carries msg.value — needs the Send bit set (1). Protocols you interact with purely through calldata get 0.

Target typeExampleOptions
Payable entry point (ETH goes in)Lido submit(), Curve ETH-pool add_liquidity(), Aave depositETH()1 (Send)
Calldata-only interactionConvex Booster deposit(), reward getReward(), ERC-20 approve()0

The failure is asymmetric and that's what makes it nasty: with the bit missing, everything configures fine and only the first real staking attempt reverts — usually in production, usually at 3am. Setting Send where it isn't needed doesn't break anything, but it widens the permission beyond what the role requires, which defeats the point of scoping.

⚠️Debugging tell: a role call that reverts only when value > 0, but succeeds as a dry run with value = 0, is almost always this bitmask — not your calldata.
Gotcha 03

Role key derivation: hash it, don't pad it

Roles v2 identifies roles by a bytes32 key. Two encodings of the same human-readable name produce different keys, and both look plausible in code review:

// ❌ WRONG — right-pads the ASCII bytes into bytes32
const roleKey = ethers.zeroPadValue(ethers.toUtf8Bytes('MY_BOT_ROLE'), 32);

// ✅ RIGHT — keccak256 of the UTF-8 bytes
const roleKey = ethers.keccak256(ethers.toUtf8Bytes('MY_BOT_ROLE'));

If your scoping script derives the key one way and your executor derives it the other, you get the perfect silent failure: a fully configured role that no one is a member of. The module doesn't reject an unknown key — it just finds no permissions under it.

Defense: derive the key in exactly one place — a shared constant module imported by both the setup script and the executor — and log the hex value at startup of each. If the two logs ever differ, you've found your bug before mainnet did.

💡Note the tooling-version trap: older Roles v1 material and some SDK examples use small integer role IDs (uint16), while v2 uses bytes32 keys. Copy-pasting between generations of examples is how the zeroPad variant sneaks in.
Gotcha 04

Multi-step protocols need their intermediate tokens whitelisted

You scope the protocol you think you're integrating, and forget the contract in the middle. The canonical example is depositing Curve LP tokens into Convex:

// The actual flow is TWO calls to TWO different contracts:
// Step 1 — approve the Booster to spend the LP token
curveLpToken.approve(CONVEX_BOOSTER, amount)   // ← call target: the LP TOKEN
// Step 2 — deposit into Convex
convexBooster.deposit(pid, amount, true)      // ← call target: the BOOSTER

Scoping the Convex Booster covers step 2 only. Step 1's target is the Curve LP token contract itself (for steCRV that's 0x06325440D014e39736583c165C2963BA99fAf14E), and it needs its own allowTarget (options 0) plus allowFunction for the approve selector. Miss it and your automation completes step 1 of a two-step flow — pardon, fails step 1 — while all your Convex-side permissions sit correct and untouched.

The general rule: walk the full call trace of every flow and scope by transaction target, not by protocol brand. Any flow involving ERC-20 approvals, wrapping, or router hops has more targets than protocols.

🔒When you do whitelist a token's approve, scope the selector on that token only — never blanket-allow the token contract. An unscoped ERC-20 target would also expose transfer(), which converts your "yield-only" role into an exfiltration path.
Gotcha 05

Deployment friction in the Safe UI

Two non-obvious snags before your module even exists:

🧩 Use the "Zodiac" Safe app, not "Zodiac Roles"
In the Safe Apps catalog there are two similarly named entries. The one labeled Zodiac — "The expansion pack for DAOs" is the one with the deploy flow for a fresh Roles Modifier attached to your Safe. The standalone Zodiac Roles app is a permissions editor for a module that already exists — it has no deploy button, and you can lose an hour hunting for one.
🧾 Clear the transaction queue first
Module deployment through the Safe app enters your Safe's transaction queue and is subject to nonce ordering. If unexecuted transactions are already queued, the deployment sits behind them and appears to hang. Execute or discard everything pending before you start.
⚠️And write the module address down immediately. If you re-run the deploy flow (say, because the queue issue above made the first attempt look dead), you get a second, empty Roles Modifier enabled on the same Safe. Now two modules exist, your scoping script may point at the wrong one, and every permission you apply lands in a module your executor never calls. Disable and remove the accidental module; keep exactly one.
Gotcha 06

Config drift: the off-chain fields that gate your on-chain calls

This one isn't in the module at all — it's in your code, and it's the most instructive failure of the set. Your executor presumably has a check like:

if (user.rolesModuleAddress && user.whitelistEnabled) {
  // execute directly via execTransactionWithRole
} else {
  // fall back to proposing to the Safe queue for manual signing
}

Now migrate your storage — JSON to SQLite, one ORM to another, a column rename for clarity — and the fields become zodiacModuleAddress / zodiacEnabled while one consumer still reads the old names. The condition evaluates falsy, and the system degrades gracefully into the wrong behavior: no error, no crash, transactions still flow — they just silently route down the manual-approval fallback path. Perfect on-chain permissions, unused.

Fallback paths are what make this class of bug invisible. Three defenses:

DefenseWhy it works
Log which path executed, every cycle"Executed via role" vs "proposed to queue" in your logs turns a silent downgrade into a visible anomaly on day one.
Grep every consumer on any field renameThe schema migration isn't done when the table is migrated; it's done when the last reader is.
Alert on fallback frequencyIf the manual path fires for a user who has a module configured, that's a bug by definition — page yourself.
Reference

A minimal working executor (ethers v6)

The smallest honest wrapper that respects everything above. The role member's EOA calls the module; the module forwards to the Safe.

const { ethers } = require('ethers');

const ROLES_ABI = [
  'function execTransactionWithRole(address to, uint256 value, bytes data, uint8 operation, bytes32 roleKey, bool shouldRevert) returns (bool)',
];

// ONE shared constant — imported by setup script AND executor (Gotcha 03)
const ROLE_KEY = ethers.keccak256(ethers.toUtf8Bytes('MY_BOT_ROLE'));

async function executeViaRole(moduleAddress, tx, signer) {
  const roles = new ethers.Contract(moduleAddress, ROLES_ABI, signer);

  // Defense in depth: assert we are calling the expected module,
  // not an address that drifted in from stale config (Gotchas 05–06)
  if (!moduleAddress) throw new Error('No Roles module configured');

  const receipt = await (await roles.execTransactionWithRole(
    tx.to,
    tx.value ?? 0n,
    tx.data ?? '0x',
    0,          // operation: CALL. Never grant DELEGATECALL to an automation role.
    ROLE_KEY,
    true        // shouldRevert — fail loudly, always
  )).wait();

  console.log(`Executed via role: ${receipt.hash}`);  // path logging (Gotcha 06)
  return receipt;
}

And the corresponding scoping sequence for one payable protocol plus one two-step flow:

// Payable protocol (e.g. a staking submit) — Send bit required
await roles.allowTarget(ROLE_KEY, STAKING_CONTRACT, 1);
await roles.allowFunction(ROLE_KEY, STAKING_CONTRACT, SEL_SUBMIT, 0);

// Two-step flow: approve on the TOKEN, deposit on the VAULT (Gotcha 04)
await roles.allowTarget(ROLE_KEY, LP_TOKEN, 0);
await roles.allowFunction(ROLE_KEY, LP_TOKEN, SEL_APPROVE, 0);
await roles.allowTarget(ROLE_KEY, VAULT, 0);
await roles.allowFunction(ROLE_KEY, VAULT, SEL_DEPOSIT, 0);
🔐Key hygiene: the role member should be a dedicated, freshly generated EOA used for nothing else. Never reuse a key that also proposes to the Safe queue or holds any other permission — one key, one role, one blast radius.
Before real funds

Verification checklist

Config transactions confirming is not verification. Run all of these against the live module before trusting it:

  • Exactly one module. In app.safe.global → Settings → Modules, confirm precisely one Roles Modifier is enabled and its address matches your config everywhere.
  • Role key parity. Log the derived bytes32 key from the setup script and from the executor at startup; the hex must be identical.
  • Positive test. Execute the smallest possible real transaction through each whitelisted function (dust amounts) and confirm on-chain state changed as expected.
  • Negative test. Attempt a call the role should not be able to make — an unwhitelisted target, an unwhitelisted selector, a transfer out — and confirm it reverts. A scope you haven't watched reject something is a scope you haven't tested.
  • Value test. For each payable target, execute once with value > 0; for each non-payable target, confirm a value-carrying call is rejected.
  • Full-flow test. Run every multi-step flow end to end (approve → deposit, claim → swap), not just its individual calls.
  • Path logging live. Confirm your logs distinguish role execution from any fallback path, and that an alert fires if a configured user hits the fallback.
  • Revocation drill. Disable the module (or revoke the role) and confirm the executor is immediately powerless. If you've never tested the off switch, you don't have one.
